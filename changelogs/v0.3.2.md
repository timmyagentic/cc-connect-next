# cc-connect-next v0.3.2

## 中文

基于最新 main 的稳定版，整合 v0.3.2 Beta 系列的最终实现。相较 v0.3.2-beta.3，本次仅更新版本元数据和发布说明，不增加运行时行为变更。

### 相较 v0.3.1

- **即时私聊完成通知**：成功回合的最终答复送达后，由同一个飞书/Lark 机器人向明确配置的回合发起人立即私聊一次，附摘要和原对话链接。默认关闭，按机器人应用配置 `completion_notify` 和 `completion_notify_users`。不追加话题通知、不查询已读、不安排延迟提醒。旧 `unread_reminder` 开关及收件人字段保留为兼容别名；旧延迟字段不再延迟发送，历史待提醒记录不会补发。配置与边界见[完成通知说明](https://github.com/timmyagentic/cc-connect-next/blob/v0.3.2/docs/completion-notifications.md)。
- **原图图集发送**：一次 `cc-connect-next send` 中重复使用 `--image`，将两张及以上本地图片按输入顺序组成双列 Card 2.0 图集，每条消息最多五张原图。单张仍为原生图片；禁用飞书卡片时逐张发送。整批上传成功后才发卡，重试复用批次 UUID，保留话题路由和传输限制；最终失败报告已确认数量，重新执行前应核实失败批次以免重复。
- **macOS 诊断**：doctor 同时展示 Agent CLI 路径、版本和有时限及深度限制的诊断进程祖先。屏幕录制、辅助功能与 Apple Events 权限明确标为未探测，终端检查不代表 daemon 权限已获验证。
- **定时任务与重启通知**：失败的 shell 任务保留退出码及脱敏诊断尾部，区分取消和超时，静默任务保持静默；检测到凭据命令行参数时省略整段输出。飞书明确拒绝向机器人未加入的聊天投递重启通知时立即结束重试，服务取消会中断退避等待，其他错误继续有界重试。
- **飞书入站顺序**：同会话附件下载和分发按接收顺序执行，后来的文字不会越过下载中的图片；过期批次定时器不会提前冲刷新批次。用户名和群名查询支持取消并各自最多等待两秒，失败时回退到 ID，不同会话仍可并行。
- **网站与文档**：更新双语产品站和配置指南，将产品链接迁移至 timmyagentic.si。

### 安装与升级

```sh
npm install -g cc-connect-next@latest
cc-connect-next --version
```

也可使用 `cc-connect-next update stable`。GitHub Latest 与 npm `latest` 发布为 v0.3.2；Beta 通道独立维护。发布不会自动启用可选功能、升级或重启本机服务。

真实飞书/Lark 收发、私聊通知和客户端跳转的端到端验收，以及各平台原生执行需分别验证；自动化测试和跨平台构建不等于这些验收已通过。

## English

Stable release from the latest main, promoting the final v0.3.2 beta implementation. Relative to v0.3.2-beta.3, this release only updates version metadata and release notes, with no additional runtime behavior changes.

### Changes since v0.3.1

- **Immediate private completion notices:** after a successful final answer is delivered, the same Feishu/Lark bot sends one private summary and original-conversation link to the explicitly configured turn owner. Disabled by default; configure `completion_notify` and `completion_notify_users` per bot app. No topic notice, read-status query or delayed reminder. Legacy unread-reminder enable/recipient keys remain aliases; the old delay is ignored and historical pending reminders are never replayed. See the [completion notification guide](https://github.com/timmyagentic/cc-connect-next/blob/v0.3.2/docs/completion-notifications.md).
- **Original-image galleries:** repeated `--image` flags in one `cc-connect-next send` invocation group local images into ordered two-column Card 2.0 galleries with up to five originals per message. Single images retain native delivery; disabling cards retains individual sends. Upload each full group before sending, reuse its UUID for retries, and preserve topic routing and limits. Final failures report the confirmed count; inspect the failed group before invoking another delivery.
- **macOS diagnostics:** doctor reports the Agent CLI path/version and bounded diagnostic process ancestry. Screen Recording, Accessibility and Apple Events permissions remain explicitly unprobed; terminal checks do not establish daemon permissions.
- **Scheduled jobs and restart notices:** retain exit codes and redacted diagnostic tails for failed shell jobs, distinguish cancellation from timeout, and keep muted output silent. Omit output containing credential-bearing CLI arguments. Stop retrying permanent Feishu rejection when the bot is outside the destination chat, interrupt backoff on service cancellation, and retain bounded retries for other errors.
- **Feishu inbound ordering:** serialize attachment handling and dispatch within a session so later text cannot overtake image downloads and stale batch timers cannot flush reset batches early. User/chat metadata lookups honor cancellation and have a two-second timeout each, falling back to IDs while unrelated sessions remain independent.
- **Website and documentation:** refresh the bilingual product site and setup guides, and migrate product links to timmyagentic.si.

### Install or update

```sh
npm install -g cc-connect-next@latest
cc-connect-next --version
```

Alternatively, run `cc-connect-next update stable`. GitHub Latest and npm `latest` publish v0.3.2; the Beta channel remains independent. Publication does not enable optional features, upgrade or restart local services.

Real Feishu/Lark messaging, private notification delivery, client navigation and native execution on each platform require separate acceptance. Automated tests and cross-platform builds do not establish those results.
