# cc-connect-next v0.1.2

## 中文

这是基于最新 `main` 的稳定版。核心交付是 issue #27 的完整实现：忙时消息可配置为「排队」或「并入当前回合」（steer），Codex 获得真正的原生 `turn/steer` 支持，飞书富卡片在 steer 后完成到最新消息的交接。已在真实飞书 + Codex app-server 环境端到端验证。

### 变化

- **忙时消息模式可配置（queue | steer）。** 新增 `[queue] busy_message_mode`（默认 `"queue"`，行为与以往完全一致），并支持项目级 `busy_message_mode` 覆盖。配置为 `"steer"` 时，回合进行中收到的普通消息会直接并入正在执行的任务，而不是排队开新回合；steer 确定不可用时安全回退到队列。
- **Codex 原生 steer。** app-server 后端通过 `turn/steer` + `expectedTurnId` 把补充内容并入进行中的回合，原回合的单一生命周期保持权威。需要在 `[projects.agent.options]` 配置 `backend = "app_server"`（本地子进程模式再加 `app_server_url = "stdio"`）。
- **修复 `/ps` 在 Codex exec 后端的并发竞态。** `/ps` 不再对正在运行的线程并发启动第二个 `codex exec resume` 进程，而是返回明确的本地化提示引导切换 app-server 后端；其他不支持 steer 能力的 agent 保持原有的回合中注入行为。
- **富卡片交接。** steer 成功后：被并入的消息立刻获得自己的卡片（「正在将此消息并入当前任务…」）；旧卡片冻结为中性灰色的「已转到更新的消息」，保留已经可见的部分回答，之后不再变化；后续进度与最终回答只渲染在最新卡片中——一个回合只有一张完成卡。连续多次 steer 依次交接，只有最新卡片保持活跃。
- **重复投递安全规则。** steer 结果未知（RPC 超时）时消息绝不自动重新排队，用户会收到明确的状态提示；只有确定未送达的失败才回退队列。
- **杂项。** 移除两个依赖本机 Cursor CLI 登录态的集成测试，本地 `go test ./...` 在未登录机器上不再必红。

### 升级

稳定版用户可以直接更新或重新安装：

```bash
cc-connect-next update
# 或
npm install -g cc-connect-next
```

启用 steer 的最小配置：

```toml
[queue]
busy_message_mode = "steer"

[projects.agent.options]
backend = "app_server"
app_server_url = "stdio"
```

`/ps <消息>` 不受该配置影响，始终是显式 steer。

## English

This is a stable release built from the latest `main`. The core delivery is the
full implementation of issue #27: busy-session messages can be configured to
**queue** or **steer** into the running turn, Codex gains true native
`turn/steer` support, and Feishu rich cards hand over to the newest message
after a steer. Verified end-to-end against real Feishu and a real Codex
app-server.

### Changes

- **Configurable busy-message mode (queue | steer).** New
  `[queue] busy_message_mode` (default `"queue"`, fully backward compatible)
  with a per-project `busy_message_mode` override. With `"steer"`, an ordinary
  message that arrives mid-turn is appended to the task already running instead
  of queueing a new turn; when steering is definitively unavailable the message
  safely falls back to the queue.
- **Native Codex steering.** The app-server backend appends input to the
  in-flight turn via `turn/steer` with the `expectedTurnId` precondition; the
  original turn's single lifecycle stays authoritative. Requires
  `backend = "app_server"` in `[projects.agent.options]` (plus
  `app_server_url = "stdio"` for the local subprocess transport).
- **`/ps` no longer races Codex exec.** On the exec backend, `/ps` no longer
  launches a concurrent `codex exec resume` against the running thread; it
  returns a clear localized hint to switch to the app-server backend. Agents
  without the steer capability keep their existing mid-turn injection behavior.
- **Rich card handoff.** After a successful steer, the steered message
  immediately gets its own card ("Adding this message to the current task...");
  the previous card freezes into a neutral grey **Continued in a newer message**
  state that retains its visible partial answer and never changes again; all
  further progress and the final answer render only in the newest card — one
  turn, one Done card. Rapid consecutive steers chain, leaving only the newest
  card active.
- **Duplicate-delivery safety.** When a steer outcome is unknown (RPC timeout),
  the message is never re-queued automatically and the user gets an explicit
  status notice; only definitively undelivered failures fall back to the queue.
- **Misc.** Removed two integration tests that required a logged-in local
  Cursor CLI, so local `go test ./...` no longer fails on logged-out machines.

### Upgrade

Stable users can update or reinstall directly:

```bash
cc-connect-next update
# or
npm install -g cc-connect-next
```

Minimal configuration to enable steering:

```toml
[queue]
busy_message_mode = "steer"

[projects.agent.options]
backend = "app_server"
app_server_url = "stdio"
```

`/ps <message>` always steers explicitly, regardless of this setting.
